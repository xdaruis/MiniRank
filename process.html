1. Plan

What we're building

MiniRank is a multi-user PHP keyword position tracker that tracks simulated keyword positions per website. All ranking data is simulated — no real search engines. It has a keyword list with trends and search, a per-keyword history page, a server-side "refresh positions" action delivered over AJAX, and seeded demo history covering ~30 days. Escalated to user accounts (register/login/logout, hashed passwords, CSRF) and multi-project/websites (projects > keywords), SQLite database.

Key decisions (and why)

DecisionChoiceReasoning
Language / framework Plain PHP 8.x, no framework The brief itself warns that large framework scaffolds work against you with free models (small context windows). Plain PHP keeps the footprint tiny and, importantly, makes security visible: PDO prepared statements and output escaping are written explicitly rather than hidden inside a framework. Also easiest for reviewers to run.
Architecture Lightweight MVC (hand-rolled) Gives a clear "where is X" answer (controllers / models / views / core) without pulling in a framework. A single public/ web root keeps config, schema, seed and controllers out of the browser URL.
Database SQLite via PDO One file, php -S just works, zero setup for reviewers. Prepared statements give parameterized queries (M6) with no server to install.
AJAX refresh Vanilla JS fetch() One button, one endpoint. No library or build step needed; ~30 lines of JS.
Routing Query params (?route=keyword.edit&id=5) Dead simple and works reliably under php -S.
Website config Per-project: projects table, site per user > project M1 starts with one configured website, but S2 stretches that to multiple projects/sites, each with its own keywords. A projects row (owned by a user, keyed by domain) replaced any hardcoded single site — the project switcher drives list/detail/refresh scope.
Seed pattern Random walk over ~30 days Positions drift up/down naturally, so the 7-day trend indicator shows realistic "improved / declined / stable".
Package manager Composer, only for PHPUnit later Core app stays dependency-free; Composer reserved for optional S6 tests.

What I would change in hindsight

Early in the brief I assumed a flat file layout; restructuring to MVC during planning was cheap (no code written yet). Lesson applied: settle the directory structure before any implementation, so later commits don't churn paths. Also: seeded the data (M2) before the CRUD (M1), so the list and detail pages had real rows to render from the start.

Prompt 1 — Requirements analysis

"Explain all the mandatory requirements of the app and the stretch goals."

Outcome: surfaced the 8 must-haves (M1–M8), 8 stretch goals (S1–S8), deliverables, and scoring weights. Flagged M6 security and the no-squash/no-force-push git rules as easy to underweight.

Prompt 2 — Generate the scaffold (failed — caught in review)

"Create the folder structure with all the PHP classes and HTML, but just boilerplate — interfaces of the PHP classes, not full implementations."

Generated: full MVC skeleton, all files lint, server boots, routes return HTTP 200.

Mistake 1 — hardcoded DB path: Database::connection() built the SQLite path itself instead of reading it from config/config.php.

Mistake 2 — no output escaping: every view echoed keyword phrases, search input, and history cells raw. Response::e() existed but was never used — an M6 XSS risk.

How caught (three checks): (1) manually looked through the files, (2) ran a second "review your own changes" pass with the agent, explicitly told to check the project's security rules, and (3) asked it whether the scaffold was too much code for a boilerplate. Lesson: a large generated diff needs more than one check — a manual pass catches what the agent misses, and a self-review pass only works when it's told which rules to check.

Fix: Database now loads the path from config/config.php; all view output wrapped in Response::e().

Prompt 3 — Tech stack

"Which PHP approach — plain PHP, a micro-framework, or a full framework? Which package manager does PHP have? Keep the stack simple to build a working product."

Outcome: plain PHP + SQLite/PDO + vanilla JS fetch(). Rationale in the decisions table above.

Prompt 4 — Refresh endpoint (wrong default — caught in planning)

"Implement the M3 refresh AJAX: 'Refresh positions' button POSTs to refresh.php and updates the page without a reload."

Mistake: refresh.php reused the front controller's Router::dispatch(), whose default route was keyword.list. A bare POST refresh.php (no ?route=) silently ran the keyword list, not the refresh action — the endpoint worked by accident of a default.

How caught: traced refresh.php → Router::dispatch(new Request()) and saw the default before wiring any JS. Fix: gave dispatch() an optional $defaultRoute param and called dispatch(new Request(), 'position.refresh') in refresh.php; verified a bare POST now returns JSON.

Lesson: a thin endpoint that delegates routing inherits the router's defaults — trace the call path before trusting it. TODO: force refresh.php's route when S2/S3 add more POST actions.

Prompt 5 — Responsive polish with Bootstrap (M8)

"M8 is responsive; should we use Bootstrap instead of hand CSS? Make it look professional for the demo."

Outcome: adopted Bootstrap 5.3 CDN — toolbar/table cards, breadcrumb, badges, sticky footer. Chose it for demo polish; cost = external CDN dependency + view markup rewrite.

Prompt 6 — Filter list (S4)

"S4: filter the keyword list by position range or movement."

Outcome: single GET form (search + trend select + min/max position + Apply/Reset). Filtering done in PHP to reuse Position::trend rather than duplicate trend logic in SQL.

Prompt 7 — Hand-rolled SVG line chart (S1)

"S1: hand-rolled inline SVG on the detail page, no dependency."

Mistake A — chart upside down: the line plotted position 1 (best) at the top, but the axis labels annotated the top with the highest number (100) and the bottom with 1 — labels contradicted the data, so it read upside down. Human caught it; fix = swap edge labels + invert the gridline formula so labels run 1 (top) → 100 (bottom).

Mistake B — tooltip could not be clicked: first used a native SVG <title>, which browsers show only on hover, never on click. Human pushed back twice. Fix = verify hit-testing, then switch to per-circle data- attrs + an app.js click tooltip. Iterated again for mobile: transparent hit circles, snap-to-nearest tap, flip-below near top, horizontal clamp.

Lesson: verify the interaction is possible before building it (native <title> is hover-only); and check chart labels against where the data physically sits — the line was right, the axis was not.

Prompt 8 — CSV export (S5)

"S5: export a keyword's position history; endpoint off the detail page."

Outcome: keyword.export GET streams Date,Position via fputcsv; ID-based filename; newest-first; invalid id redirects. Fixed a PHP 8.4 deprecation (explicit $escape). Adjacent fix: the detail badge relied on a position key find() never returns, so it silently never rendered.

Prompt 9 — Refresh CSRF transport (JSON body ignored — caught)

"Send the CSRF token with the refresh POST and enforce it on the endpoint."

Mistake: app.js posted a JSON body; PositionController::refresh read $_POST (Csrf::verify(post('csrf_token'))), so the token never arrived and every refresh was rejected. JSON request bodies do not populate $_POST.

How caught: live-probe POST returned HTTP 403 Invalid CSRF token — the guard proved the handler saw an empty token. Fix: switched to a FormData POST field + a <meta name="csrf-token"> consumed by JS.

Adjacent gotcha: a logged-in session POSTing to auth.register runs Auth::login(), which session_regenerate_id(true)s and rewrites the acting session — during audit probes this silently swapped the "demo" session to the new user. Kept test sessions on separate cookie jars from then on. Lesson: match the fetch body format to the server read path ($_POST vs php://input), and keep probe sessions isolated from mutations that regenerate the session.

Prompt 10 — PHPUnit suite (S6) + README (M7) + behavioral fixes

"Add Docker + PHPUnit and the setup README; then harden the bugs found in a code smell pass and wire it into CI."

Outcome: PHPUnit ^11 suite — security invariants (ownership isolation, CSRF, POST-only mutations), auth flows (login/register/logout), list filters, trend/refresh logic, model edges. Restructured into tests/Models/, tests/Core/, tests/Http/ + tests/Support/; composer autoload-dev; .env/DATABASE_PATH override so tests never touch the real DB; a Response::redirect abort seam lets HTTP tests assert redirects instead of hitting exit. README expanded (M7): requirements, macOS/Ubuntu install, seed/run/test.

Behavioral fixes shipped: trend fallback bounded to the 7-day window (no longer compares against the oldest-ever row); batch refresh wrapped in a transaction (rollback on mid-batch failure); keyword access (findOwned) scoped to the active project across edit/detail/export/delete.

Mistake 1 — namespace break after restructure: moving tests into sub-namespaces left the catch (RedirectSignal) clauses referencing the now-wrong class, failing the delete tests. Caught by running the suite; fix = explicit use App\Tests\Support\RedirectSignal;.

Mistake 2 — scope breadth: when adding the optional $projectId to findOwned, it seemed a delete-only change; reading the sibling handlers showed edit/detail/export also fetch by id and needed the same project scope. Fix = scope all four call sites. Lesson: signature changes invite revisiting every call site, not just the one in hand.

Prompt 11 — S7 Docker + dockerized tests + CI

"Implement Docker for dev and prod, make the tests runnable in Docker, restructure the README around both install paths, and wire the dockerized tests into GitHub Actions."

Outcome: single multi-target Dockerfile — dev (bind-mounted source + built-in server), prod (nginx + php-fpm, one-shot seed, non-root, named volumes), test (Composer-enabled PHPUnit runner). Three compose files; README rewritten around two run paths (self-run vs Docker, zero local deps) with tests under both; .github/workflows/ci.yml calls docker compose -f docker-compose.test.yml run --rm test. 65 tests pass under Docker.

Gotcha 1 — extensions already compiled: php:8.2 ships pdo_sqlite/sqlite3/mbstring; the first build ran docker-php-ext-install + apt needlessly and failed on "already loaded". Fix = drop the install step entirely. Lesson: verify what the base image already provides before compiling.

Gotcha 2 — named volume hid seed files: mounting the DB volume over database/ shadowed seed.php/schema.sql, so seeding failed ("could not open input file"). Fix = persist the DB on a dedicated /var/www/data path via DATABASE_PATH, kept separate from the code directory.

Gotcha 3 — port 8080 collision: Docker Desktop's proxy already held 8080; prod remapped to 8081 (README/compose updated to match).

Gotcha 4 — Composer needs unzip: --prefer-dist extraction failed in the test image until unzip was installed via apt.

Prompt 12 — Seed expansion (payload.com, 105 XSS keywords)

"Let's plan for the next feature '- [ ] Seed expansion — OPTIONAL — extend database/seed.php to add payload.com/payload domains and generate 105 keywords (plus Pagination, next item).'"

Outcome: single payload.com project holding 105 unique XSS-payload keyword phrases — real vectors (OWASP/PortSwigger/html5sec classes + encodings) plus deterministic gibberish-arg variants to reach exactly 105, collision-free via array keys + a count assert. Per-keyword drift/amp/start randomized, so the 30-day random-walk position generation is unchanged in shape. 110 keywords total (5 pizzeria + 105 payload); summary now reports per-project counts. The corpus doubles as M6 validation data — payloads must render escaped, never execute.

Prompt 13 — Dev container auto-reseed (diagnostic)

"why my docker dev container doesn't regenerate the db with the seed script?"

Root cause: the dev container persists SQLite on a named volume db_data at /var/www/data, decoupled from the host database/ dir. entrypoint.sh seeded only if the DB file was absent, so the old volume's DB survived down/up and the updated (bind-mounted) seed.php never ran.

Fix: dev entrypoint.sh now always runs the idempotent seed on container start. Dev-only — prod keeps a separate one-shot seed service and distinct volumes, so it is untouched. Required an image rebuild because entrypoint.sh is COPY'd into the image, not bind-mounted.

Lesson: named volumes survive down/up; a "seed if missing" guard never refreshes an existing volume.

Prompt 14 — SQLi + XSS attack tests

"Let's plan for the next feature '- [ ] SQLi + XSS attack tests — OPTIONAL — add SQL-injection and XSS payload cases to the PHPUnit suite to prove the M6 escaping/prepared-statement invariants under attack input.'"

Outcome: tests/Http/AttackTest.php — SQLi cases prove prepared statements bind literally (search UNION/OR injection leaks nothing, DROP TABLE not executed, add/edit injection stored as literal) and XSS cases prove Response::e() escaping across search reflection, list, detail, edit form, and an add-then-render round-trip. Verified live too (payload phrases render &lt;script&gt;-escaped, never raw). Footprint: full suite grew to 104 tests.

Prompt 15 — Pagination

"Let's plan for the next feature '- [ ] Pagination — OPTIONAL — page/per_page on keyword list + position history; index on positions(keyword_id, captured_at) already present.'"

Outcome: page/per_page on the keyword list (default 20) and the position-history table (default 15). Pagination is a post-filter PHP slice: the list's move/position filters run in PHP (Position::trend), so SQL LIMIT on the filtered set is impossible. A shared partials/pagination.php serves both pages; the detail chart keeps the full history while only the table paginates. Covered by tests/Http/PaginationTest.php.

Nav iteration (user feedback): the first nav (Prev/Next + 5-number window) let users only page 1-by-1 and lacked bounds, and the 105 count rendered twice (card header + nav). Fix = added First / Last buttons and a numeric page-jump form, and removed the duplicated "N rows" line (count now shown once in the card header). The "collapsed page numbers with clickable ellipsis" pattern was discussed and deferred — current First/Last + jump is "ok for a demo".

3. Retrospective

What I've done good

  • Always planned before writing any code.
  • Always checked the agent's output in the diff/review panel before building on it.
  • Manually clicked through the pages, the features, and the edge cases — didn't just trust a passing test.
  • Updated this process document at the end of every session.

What I would change

  • Spend more time writing less, more maintainable code and following best practices.
  • Lean further into PHP — it's simple and robust — and go deeper on how each piece actually works.
  • Use an ORM and a proper database (MySQL/Postgres) instead of SQLite.

Agent logic flaws caught by human review

  • The S6-before-S2/S3 reorder I proposed was pointless — those tests cover logic S2 doesn't touch, so no rewrite was needed. Human caught it; I reverted.
  • The chart axis contradicted the data (labels vs where the line sat), and a native <title> can't be clicked. Both fixed.
  • The refresh CSRF failed because I sent a JSON body but the server read $_POST; and a live-probe session got swapped by re-login. Fixed, probes isolated.
