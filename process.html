Candidate: MiniRank keyword position tracker · Window: 14.08 – 18.08.2026 · Status: skeleton built, feature implementation pending

1. Plan

What we're building

MiniRank is a single-user full-stack PHP app that tracks simulated keyword positions for one website. All ranking data is simulated — no real search engines. It has a keyword list with trends and search, a per-keyword history page, a server-side "refresh positions" action delivered over AJAX, and seeded demo history covering ~30 days. No login (single user), SQLite database.

Key decisions (and why)

DecisionChoiceReasoning
Language / framework Plain PHP 8.x, no framework The brief itself warns that large framework scaffolds work against you with free models (small context windows). Plain PHP keeps the footprint tiny and, importantly, makes security visible: PDO prepared statements and output escaping are written explicitly rather than hidden inside a framework. Also easiest for reviewers to run.
Architecture Lightweight MVC (hand-rolled) Gives a clear "where is X" answer (controllers / models / views / core) without pulling in a framework. A single public/ web root keeps config, schema, seed and controllers out of the browser URL.
Database SQLite via PDO One file, php -S just works, zero setup for reviewers. Prepared statements give parameterized queries (M6) with no server to install.
AJAX refresh Vanilla JS fetch() One button, one endpoint. No library or build step needed; ~30 lines of JS.
Routing Query params (?route=keyword.edit&id=5) Dead simple and works reliably under php -S.
Website config One site hardcoded in config M1 requires a single configured website — no need to model multiple sites.
Seed pattern Random walk over ~30 days Positions drift up/down naturally, so the 7-day trend indicator shows realistic "improved / declined / stable".
Package manager Composer, only for PHPUnit later Core app stays dependency-free; Composer reserved for optional S6 tests.

Early in the brief I assumed a flat file layout; restructuring to MVC during planning was cheap (no code written yet). Lesson applied: settle the directory structure before any implementation, so later commits don't churn paths.

2. Prompts & fixes

Prompts marked failed are included deliberately — recovering from a bad prompt is part of the assessment.

Session links

Prompt 1 — Understanding the requirements

"Explain all the mandatory requirements of the app and the stretch goals. Use caveman style."

Outcome: surfaced the 8 must-haves (M1–M8), 8 stretch goals (S1–S8), deliverables, and scoring weights in plain language. Confirmed security (M6) and the "no squashing / no force-push" git rules are easy to underweight — good that they were made explicit early.

Prompt 2 — Tech stack decision

"Which PHP approach should we use — plain PHP, a micro-framework, or a full framework? Which package manager does PHP have? Keep the stack simple to build a working product."

Outcome: landed on plain PHP (Composer is PHP's package manager), SQLite/PDO, vanilla JS fetch(). The framework choice is deliberately justified in section 1 and will be explained in the write-up, as the brief requires.

Prompt 3 — Project structure

"The project structure is too flat. Can we have some MVC-style folders instead?"

Outcome: restructured to a lightweight MVC layout with a public/ web root, separating controllers, models, views and core helpers — without adding framework weight.

Prompt 4 — Boilerplate skeleton

"Create the folder structure with all the PHP classes and HTML, but just boilerplate — interfaces of the PHP classes, not full implementations."

Outcome: full MVC skeleton generated and verified — every file lints, the server boots, and keyword.list + refresh routes both return HTTP 200. Models are pure stubs (return []/null); controllers only wire views to models.

Prompt 5 — Review caught unescaped output

"Can you review all the staged changes and tell me if the boilerplate isn't too much?"
"…(the generated skeleton echoed view values without escaping)…"

Review finding: the generated views echoed keyword phrases, search input, and history cells raw — Response::e() existed but was never used. That is exactly the M6 output-escaping violation the brief warns free models will write. Caught during review (not by the model), then fixed by wrapping every echoed value in Response::e(). This is the required "caught the AI's mistake" moment: the boilerplate looked fine but shipped unescaped output, and the reviewer gate is what stopped it.

A genuinely failed prompt (one that produced a bug, not just an oversight) will still be added during feature implementation. Prompt 5 here documents a security gap caught in review — already evidence of the verify-everything discipline the assessment wants.

3. Retrospective

What's going well

  • Planning was done before any code — matches the assessment's "plan first" advice and saves free-model quota.
  • Structure and tech choices are settled and documented, so implementation commits won't churn.
  • Security (M6) and git-hygiene rules were identified as easy to underweight and flagged early.
  • The skeleton was reviewed as a gate: unescaped view output (an M6 violation) was caught before any real data flowed through the app.

What I would do differently

  • Ask for the public/ web-root separation from the very first skeleton, not after a first draft.
  • Write the final process document incrementally as I go, rather than drafting it late — it's a graded deliverable (10%).

Effort so far

Approx. hours: ~3h (requirements analysis, tech decisions, planning docs, agent rules, MVC skeleton, escaping fix).
